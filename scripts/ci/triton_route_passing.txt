# Tests that pass THROUGH the Triton codegen route.
# Gated by scripts/ci/triton_route_sweep.py; regenerate with
#   python scripts/ci/triton_route_sweep.py --all --update-allowlist
# A test that passes without emitting a kernel is deliberately absent.
# WHAT WAS BLOCKED HERE AND IS NOT. tests/models/test_swinv2.py stopped after
# 26 kernels because transformers' Swinv2Layer.get_attn_mask builds its
# shifted-window mask with `torch.zeros(...)` and no `device=`, so an
# input-independent constant stayed on the host INSIDE the traced graph and
# Inductor emitted a C++ kernel for it -- which its own CPU vectorizer then
# failed to compile (`decltype` of a scalar float, then
# `Vectorized<float>::blendv`), reproducible with stock torch and PyTorchSim not
# imported at all.
#
# Two ways out were measured. `cpp.simdlen = 0` makes the C++ compile, and was
# declined: it is process-wide and it hides someone else's defect. Naming the
# default device for the compiled call removes the island instead -- the mask is
# built on the device and this backend compiles it like any other elementwise
# work. 26 kernels and a compile error before; 27 kernels, no C++ kernel at all,
# and 4.77e-06 after. The test carries the two-line scope and the reasoning.
#
# WHAT SD1.5 NEEDED, since it is the newest and the longest entry here.
# tests/models/Diffusion/test_diffusion.py runs the UNet2DConditionModel at
# reduced channel counts: 87 kernels compiled, 220 executed, and it stopped
# three times before it ran.
#   buf3    GroupNorm's Welford mean, 32 of 32 channels equal to the mean over
#           the whole tile -- the gather's rank-1 index vector pinned the loop
#           body to the reduction axis while the accumulators kept the other
#           one, because lib_axis_graph had no scf.for edge (triton-npu).
#   kernel 83  a segfault on the SECOND trip round a reduction loop: a gather
#           index non-affine in the loop variable had the loop offset added to
#           the base as well as carried in the index tensor (triton_shared,
#           PtrAnalysis::rebuildAsGatherScatter).
#   buf20   eight reports against add_N nodes nothing materialises -- the
#           per-kernel verify checked buffers a kernel only READS, and
#           Inductor can name an in_out_ptr the kernel never stores to.
# Runtime here is about 11 minutes, inside the sweep's 1800s default.
#
# WHY test_llama3x.py IS HERE WHEN test_llama3.py ALREADY IS. It gates a width,
# not an architecture. test_llama3.py runs 1024 hidden, which puts head_dim at
# 32 -- a quarter of the array -- and no shipped Llama is that shape, so it says
# nothing about how the real block tiles. test_llama3x's default is one layer of
# the real 8B block (4096 hidden, head_dim 128, SwiGLU 14336) plus the vocab
# projection: 285M parameters, 23 kernels, 8.58e-06, 301s. It also carries the
# 3.2 shapes -- 3B's n_rep=3 is the first non-power-of-two GQA repeat in the
# suite -- and 3.1's rope scaling, which is guarded because that scaling folds
# into inv_freq at construction and a test can otherwise "pass 3.1" while
# compiling Llama 3's graph unchanged. Nothing here was broken when it was
# written; the entry is a floor, not a fix.
#
# WHAT test_gemma.py ADDS that no other entry covers. It gates a family across
# three generations, so its default runs three presets, one per generation:
# 7b + 2-2b + 3-1b. Measured the way this file runs it -- all three in one
# process -- at 1137s and 64 unique kernels, inside the 1800s default. Each
# preset's max diff there is identical to its own isolated run, so the three
# share codegen rather than colliding in it.
#
# Gemma 1 (7b, and 2b behind it): MQA -- num_key_value_heads=1, so ONE kv head
# is broadcast across eight query heads, where every other GQA repeat in the
# suite is 1, 2, 3, 4, 6, 7 or 8-into-8. head_dim 256, twice the suite's
# previous maximum. head_dim decoupled from hidden at 7B (16 * 256 = 4096
# against 3072), so q_proj is not square and o_proj shrinks. GeGLU, where every
# other gated MLP here is SwiGLU. And GemmaRMSNorm scales by (1 + w) off a
# zero-initialised weight, not by w, which the test checks by pushing a unit
# vector through the norm rather than by reading the config -- a backend that
# folded the two RMSNorm forms together would pass everything else in this file
# and fail only there.
#
# Gemma 2 (2-2b): local and global attention ALTERNATE, so the preset runs two
# layers -- one of each -- and they compile to separate attention kernels (24
# unique against 38 executed). Logit soft-capping adds a tanh on the
# [b, h, seq, seq] scores and another on [b, seq, vocab]; nothing else here
# caps. Four RMSNorms per layer against Llama's two. 2-27b-scalar carries 27B's
# query_pre_attn_scalar of 144 against head_dim 128, the one Gemma where the
# pre-attention scale is not head_dim ** -0.5.
#
# Gemma 3 (3-1b): TWO ROPE BASES in one model -- 10000 on local layers, 1000000
# on global, as two rotary modules -- where every other model here has one
# inv_freq. The preset runs six layers, one full 5:1 period, so the single
# global layer actually runs; 25 unique kernels across 100 executions.
#
# THE WINDOW IS SCALED TO THE SEQUENCE, AND THAT IS LOAD-BEARING. Both shipped
# configs use a 4096-token window, which at seq 32 masks ZERO elements: the
# local layers would be byte-identical to the global ones and the alternation
# would go untested while the test still passed. The presets use window 8 and
# _assert_character refuses any preset whose window is not strictly inside its
# seq, so that particular vacuous pass cannot happen quietly.
#
# Nothing was blocked: all three generations ran end to end on the first
# attempt, with no backend change. The entry is a floor, not a fix.
# test_mllama.py IS THE ONE THAT NEEDED A BACKEND FIX. Llama 3.2 Vision's
# cross-attention decoder layer stopped in triton-npu's absorb_layout with
# "indexing map cannot take the move": a single-input elementwise generic whose
# move drops a unit middle axis, leaving no operand naming that dim, so linalg
# could not infer the loop's bound -- which for a unit dim is 1. Fixed in
# triton-npu 2988424, and the pin in thirdparty/triton-npu.json moves with it.
# Both towers run: vision 4.5300e-06, text 4.1723e-06, 8m07s for the pair
# (4.2915e-06 / 3.4019e-06 before the transformers 4.51 -> 5.15 step; the numbers
# moved within the decade and the entry did not need a source change).
# The vision width is NOT the real 1280 on purpose -- test_vit.py and
# test_clip.py already gate ViT-shaped attention at 768, and what was unproven
# was the tile structure and the local/global split, which scaling keeps.
#
# test_llama4.py IS THE ONE THAT NEEDED TWO. Llama 4 is the first break in the
# family since 3 and it carries four new things at once -- MoE in every layer,
# a NoPE period, per-head qk_norm, and chunked attention -- so it stopped three
# times and only the last stop was about any of those four. `aten.polar` (the
# complex-valued rotary, which no other model here builds) needed PyTorchSim
# 3fdcab7 to become a view over a real pair; then the model compiled and
# answered WRONG at max abs diff 1.31, because the MoE router fills with -inf
# and scatters the top-k in and `_roles` gave that buffer a fresh allocation.
# 8d8e2ed fixed it and tests/ops/misc/test_inplace_partial_write.py pins it.
# 147,874,816 parameters, 31 kernels, 4.7684e-06, 8m00s at --preset small.
# Fifteen ops run eager, 11 fill_ and 4 topk; the complex rotary is NOT among
# them any more -- extension_complex_to_real (84ad277), written against
# DeepSeek-V2, covers Llama 4's complex path unchanged and took twenty calls off
# that list. The gate is 1024 hidden on purpose: --preset scout builds Scout's
# real 5120 width, compiles all 30 kernels, and dies in spike because tnpu's
# wrapper doubles every buffer and the 1.25 GiB expert stack then fails to
# calloc. That is a wrapper limit, not a model one, and it is written up in the
# test's docstring.
#
# WHY tests/models/Qwen/test_qwen_next.py IS A SECOND QWEN ENTRY. It is the
# families transformers 5.x added, and they are not shapes on the block
# test_qwen.py gates: qwen3_5 and qwen3_next are LINEAR attention, whose
# recurrence unrolls per position -- 121 and 132 kernels at seq 16 against the
# 19 a Qwen3 layer takes -- and qwen3_5 puts a Conv1d in the block, which needs
# the conv1d-to-conv2d registration or it falls to an extern this device has no
# implementation for. Its own gate is `qwen3_5` plus `qwen3_vl_moe`, one of each
# kind: a linear-attention family and an MoE one, the second of which routes
# through extension_counting_sort and so keeps that rewrite from being a
# one-model patch. The audio families in that file run TEXT ONLY; their encoders
# are not covered by it and its docstring says where they stop.
#
# WHY tests/models/Qwen/test_qwen.py RUNS TWO PRESETS WHERE EVERY OTHER ENTRY
# RUNS ONE. It gates a family, not a model: Qwen2/2.5 carry a QKV bias that no
# other block in this suite has, Qwen3 drops it and adds an RMSNorm per head
# over head_dim (q_norm/k_norm), and the two MoE lines differ from each other by
# a gated shared expert. No single preset is the whole claim, so the default
# runs `3-8b` (Qwen3 at its real 4096 width, 260M params, 19 kernels, 6.68e-06)
# and `2-moe` (the QKV bias plus routed + shared-expert MoE, 36 kernels,
# 2.42e-06) -- 519s for the no-argument run, on a machine that was running four
# other model tests at the time. n_rep=7 at the real 7B width, Qwen3-MoE and the decoupled
# head_dim are one `--preset` each and are not in the gate.
#
# AND WHAT IT COST TO GET THERE, since the entry would otherwise look free:
# Qwen3's q_norm fuses with rope into a persistent reduction, 27 live
# scratchpad tiles, 1625120 bytes/lane against a 131072 budget. The retry in
# triton_backend/codecache.py halved R0_BLOCK, which a persistent reduction
# bakes into its own body -- so 128, 8 and 1 all measured the SAME overflow and
# the kernel was refused. It now shrinks only a block the kernel takes as an
# argument, XBLOCK when a reduction takes none.
#
# WHY tests/models/Yolo/test_yolo.py GATES TWO OF NINE VERSIONS. It covers the
# ultralytics model parser, one preset per version directory under
# ultralytics/cfg/models -- v3, v5, v6, v8, v9, v10, 11, 12, 26 -- built from
# YAML with random weights, no checkpoint and no torch.hub. The existing
# tests/models/Yolov5/test_yolov5.py keeps the hub path and the pretrained
# weights; this file is the config-built counterpart across generations, and
# the parser fits its modern anchor-free head onto every version, so a preset
# here is a claim about the BACKBONE and NECK.
#
# v5 (C3 + SPPF) and v8 (C2f) pass at 1.85e-05 and 1.15e-05 relative and are
# the gate: 1128s for the no-argument run, measured the way the sweep runs it.
# ALL NINE PASS. The other seven are out of the gate, not out of coverage, and
# none of them was ever merely "not tried" -- each had a measured stop, written
# out in the test's docstring, and each is fixed:
#   v6            PASSES at 1.98e-05, 72 kernels, 498s. It had stopped in the
#                 DEVICE: Inductor's conv lowering does not offer the Triton
#                 template a transposed convolution, so its ConvTranspose2d
#                 neck went out as extern_kernels.convolution and dispatched to
#                 convolution_overrideable, which raises. Registering that op
#                 would have been the wrong fix -- PyTorch's own
#                 CompositeExplicitAutograd kernel for it IS the raise and an
#                 alias key covers PrivateUse1, so the CPU fallback never gets
#                 a turn, and a kernel would run the convolution on the host
#                 and simulate nothing. Fixed by not emitting it:
#                 PyTorchSimCodegen/inductor_patches.py rewrites a transposed
#                 convolution as the direct one it is, wrapped around the
#                 convolution lowering. OUT OF THE GATE ON RUNTIME -- 498s
#                 would take the gate to about 1600s against an 1800s budget
#                 already seen to swell to 1578s under load. It is the only
#                 version here kept out by a budget rather than by a toolchain.
#   v3, v9        PASS at 2.93e-06 and 1.15e-04. Both were one bug:
#                 PtrState::rebuildAsGatherScatter zeroed the constant offset
#                 that distinguishes a pool window's four loads, so the four
#                 became one, CSE merged them and canonicalize folded the max
#                 away -- v3 returned silu of the top-left element, v9's
#                 avg_pool returned (a+a+a+a)/4. Fixed in PSAL-POSTECH/
#                 triton_shared b6c3e60 (1304 of 1311 dumped kernels
#                 byte-identical after it; all 7 that changed are pools).
#   v10 11 12 26  PASS at 2.64e-05, 1.25e-05, 2.67e-05, 5.65e-05, after TWO
#                 defects in the same kernel -- the PSA depthwise conv. It
#                 SEGFAULTED on the old pin (fixed by triton-npu a616ea5, which
#                 removed a p11 repair measured as never firing and which this
#                 kernel drives True twice), and then returned wrong numbers
#                 because all 128 channels read channel 0's BatchNorm
#                 parameters: applyUnstructuredMask rebuilds the load as a
#                 gather for its MASK, not its address, and divided the parked
#                 `group` offset by the broadcast dim's stride of 0. Fixed in
#                 triton_shared 99dc6bc. That defect has a far cheaper witness
#                 than a PSA block, found while verifying v6: a plain
#                 nn.Conv2d at groups > 1 WITH A BIAS. The convolution comes
#                 out exact and the bias lands on the wrong channels --
#                 channel c gets bias[c % (OUT_C // GROUPS)], so a depthwise
#                 layer gets bias[0] everywhere. MobileNet-v2 does not see it
#                 because its convolutions are bias=False.
#
# ADDING THE SEVEN TO THE GATE is a runtime decision, not a correctness one:
# the six above cost 1652s + 384s + 1024s + 907s + 1252s + 1169s run separately,
# which is several sweep budgets. Whoever adds them should split the file's
# no-argument run rather than lengthen one job.
#
# THE PIN MOVED WITH THIS, and it is a MERGE rather than a bump. 2988424 (the
# p09 unit-axis fix test_mllama.py is gated on) is NOT an ancestor of triton-npu
# develop -- it carries five commits that never landed there -- so pinning
# develop alone would have taken a616ea5 and dropped the p09 fix, and mllama
# would have started failing for a reason nothing in this file mentions.
# thirdparty/triton-npu.json now points at 98744f7, develop merged with that
# line -- one commit carrying p09 (mllama), p11 (the YOLO segfault) and p13
# (7aec83d, Qwen2-VL's replicate axes, which landed on develop while this pin
# was being moved). Re-measured on it: resnet, mllama (both towers, 4.2915e-06
# / 3.4019e-06) and this gate (1.85e-05 / 1.15e-05) all pass, and the four YOLO
# versions above return max rels identical to their a616ea5 runs to every
# digit.
